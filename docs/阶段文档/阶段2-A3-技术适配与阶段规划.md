# 阶段 2 A3 技术开发文档｜技术适配与阶段规划

日期：2026-10-08。版本：V1.1 工程交付与待验（先形成 V1.0 开工稿，再实现和验证，最后补入交付事实）。依据：主 PRD V1.1 FR06、FR07，必要 FR04/FR05/FR14/FR24；阶段 1 技术适配与通用手册第二、三部分。

开工依据：产品负责人在已展示 A3 范围与待验边界后回复“继续吧，还是按照我的规则”。记录仅限 A3 未受影响工程的推进例外，保留 A1/A2 真实模型、缩放/真机及依赖风险。不是阶段通过、模型付费、资料外发或开发执行授权。顺序为本文档 → 工程与验证 → 证据及状态 → 本地提交。

## 一、阶段目标

产品工厂针对用户管理的项目，复用已冻结需求基线，检查环境并辅助形成技术适配声明，经人工确认后整理版本、阶段和任务计划；用户能看清保留工程、范围、依赖、验收和阻塞。此为工厂新能力，不重复阶段 1 对工厂自身的技术选型。

链路：项目需求页 → 技术与计划页 → 只读环境检查 → 基线绑定的技术适配草稿 → 编辑与确认 → 版本/阶段/任务草稿 → 依赖及覆盖检查 → 人工确认计划 → 刷新/重启接续。

范围为准备和交接，不启动业务开发任务、不安装依赖、不运行项目脚本、不写原工程、不部署。没有基线时可检查环境，但不能生成可确认的方案或计划。冻结了新基线或环境依赖声明变化时，旧确认保留历史并显示需重新核对。

## 二、技术适配摘要

沿用 FastAPI/Pydantic、SQLite/SQLAlchemy/Alembic、Next.js/TypeScript；增量增加规划资产及项目内最小验收页，不替换 A1/A2 工程、依赖和用户目录。

本轮按确定性规则及显式编辑组织草稿，页面标注“规则建议，待人工核对”，不冒充模型生成。新空工程建议沿用已定 Web/后端基线；已识别工程优先保留实际技术栈，不为模板重构；未知工程明确待核对。业务方案是否合适由人工确认。

## 三、技术栈与模型

无需新增库、云资源或模型契约。本轮不进行模型调用，无 Prompt；A2 模型服务、Key 配置与预算保持兼容、未启用状态和待验结论不变。自动生成的是有来源的规则草稿，用户可修改。AI 更深入的方案分析需单独接入受控契约及真实验证，不能以规则建议冒充。

## 四、环境与配置

本机前端 3000、后端 8765，沿用 Host/Origin/服务端令牌保护。项目路径受已授权根目录约束，不扩大访问范围。

检查 Python 当前运行时，Node/Git 仅执行受信系统或已批准本机运行时目录中的固定 --version 配方（不通过 Shell 或仓库工作目录；仅允许标准系统安装目录、Homebrew node@22 目录，以及 pi-node/nvm/fnm 固定安装根内已解析的 Node 二进制，拒绝任意项目 PATH 候选，不读取 npm scripts，不运行安装）。每次最多两条外部版本命令，每条超时 2 秒；只保留提取出的版本，不保存原始输出。缺工具给“照着装”建议，不自动安装。环境结果展示方法、时间、适用范围及局限。

只读检查目录读/写权限标志、可用磁盘、批准模型配置状态、固定依赖声明位置（根目录及 frontend/backend）。单声明最多 64 KiB、固定最多 6 个文件，拒绝符号链接与非普通文件；不扫描 .env 或业务原文。依赖只保存已识别框架与文件指纹，不保存完整依赖内容。权限检查不写探针文件；依赖可用不等于项目已构建或运行，实际执行器本轮未交付。

## 五、项目结构

- 新增 backend/app/planning_schemas.py：所有输入、输出、枚举与长度。
- 新增 backend/app/planning.py：环境配方、方案与计划修订、来源校验、依赖图、确认及失效判断。
- db.py 与新 Alembic 0003：追加式规划资产；原迁移不改写、不删除旧数据。
- frontend/app/projects/[id]/planning/：最小技术与计划页；需求页增加入口。
- backend/tests/test_planning.py：覆盖状态、冲突、幂等、图校验、恢复和安全。
- docs/evidence/阶段2-A3/：截图、可操作地址和闸门表。

## 六、数据、资产与状态

PlanningAsset 持久化 id、project_id、kind、revision、baseline_id、payload、created_at；kind 受控为 environment/technical/plan/technical_approval/plan_approval。每类修订在项目内递增，保存新增记录，旧草稿与确认不覆盖。基线引用已存在的不可变 RequirementRecord；环境本身不要求基线。确认记录写入本机操作者、说明、来源修订及内容哈希；审计不记录全文。

技术适配正文：需求理解、推荐方案、保留工程、按需模块、模板偏离原因、增量费用、暂缓项、数据流、通过条件、风险。声明绑定环境检查及需求基线。用户确认前只是准备草稿；确认不是执行许可。

计划正文：版本标识/名称、阶段与可选父阶段、范围内外、交付目标、依赖、任务；任务关联需求编号，或明确缺陷标识/基础设施理由。按基线目标版本与 P0/P1/P2 组织初始实现/验证阶段；排序属于规则建议。所有基线需求必须覆盖，需求的原验收文本由后端带入、不可删减；每阶段继承固定十项闸门，具体不适用须将来验收时有依据，不能在规划时删除。

可保存有阻塞的计划草稿，但不能确认可交接计划。检查包括：缺少版本/阶段/任务，引用不存在、重复编号、依赖成环（版本/阶段/任务及父阶段），阶段依赖与任务跨阶段依赖不一致，需求缺漏、未知需求、新增范围、版本错配、优先级弱化和必要输入缺失。阶段准备/技术方案/计划确认与未来执行状态分开；本轮 execution_supported=false，不能展示任务已经执行或阶段已通过。

未冻结的需求草稿变更仅提示未纳入当前基线；新冻结基线使旧方案/计划确认失效，须重新生成或显式核对绑定新基线。新技术方案修订使绑定旧方案的计划需重新核对；原确认保留历史。

## 七、API / 工具设计

统一前缀 /api/v1/factory/projects/{id}/planning；所有 POST 需 Origin 与 Idempotency-Key，确认要求 expected_revision、expected_hash 和说明。错误统一 {"error":{"code":"…","message":"…"}}，不回显秘密或堆栈。

| 方法/路径 | 输入 | 输出 | 主要错误 |
| --- | --- | --- | --- |
| GET / | 无 | 当前环境、技术/计划草稿、全部修订摘要、确认有效性、阻塞/提醒、可交接状态及 execution_supported=false | NOT_FOUND |
| POST /environment | 空对象 | 环境检查资产、方法及限制；缺工具或损坏声明记录为检查阻塞 | PATH_FORBIDDEN、NOT_FOUND |
| POST /technical/generate | baseline_id、environment_id、expected_revision | 来源为规则建议的新技术草稿 | NOT_FOUND、BASELINE_STALE、REVISION_CONFLICT |
| POST /technical/revisions | expected_revision、baseline_id、environment_id、正文 | 新草稿修订与待核对项 | INPUT_INVALID、REVISION_CONFLICT |
| POST /technical/confirm | expected_revision、expected_hash、说明 | 不可变确认记录及绑定摘要 | PLAN_BLOCKED、REVISION_CONFLICT |
| POST /plans/generate | technical_id、expected_revision | 绑定已确认方案的规则计划草稿 | TECHNICAL_REQUIRED、INPUT_STALE、REVISION_CONFLICT |
| POST /plans/revisions | expected_revision、technical_id、版本/阶段/任务正文 | 新修订及完整检查结果 | INPUT_INVALID、REVISION_CONFLICT |
| POST /plans/confirm | expected_revision、expected_hash、说明 | 人工确认计划，状态仅为可交接 | PLAN_BLOCKED、REVISION_CONFLICT |
| GET /assets/{asset_id} | 无 | 当前项目历史资产，含原始快照、来源和创建时间 | NOT_FOUND |

确认前重新检查最新基线、方案来源、环境有效期 15 分钟和当前依赖声明指纹，改变或过期要求重新检查；不能靠前端按钮隐藏替代。幂等与修订/确认/审计在数据库写事务处理，重启后读取同一资产。检查同步受限，无模型/SSE/长运行业务任务。

输入/输出均采用严格结构；额外字段拒绝，正文、说明不能仅含空白。版本最多 100、阶段最多 200、任务最多 300，每组依赖最多 100 个，引用编号最长 16 字符；规划写请求还受前端代理整包 1 MiB 限制，数量上限与正文长度上限须同时满足。原 A1/A2 请求上限保持 128 KiB。生成方案摘要超长时带明确截断标记，完整基线仍可核对；生成后同样结构校验。计划原验收文本与十项闸门由服务端持久化，客户端不能在保存正文时替换或删除。

页面在加载、保存与主动检查时刷新有效性，不持续轮询；交接前点击“重新检查计划”。来源过期时，先重新检查环境，选择新环境保存并确认方案；旧计划需重新生成，或逐项核对、编辑并保存以绑定当前已确认方案，再重新人工确认。旧确认不自动继承。检查事实不等于全部依赖兼容、项目构建成功或业务性能通过。

## 八、Prompt 设计

本轮无 Prompt 或外发上下文；规则仅使用当前项目基线和经过限制的环境结果。规则草稿 source=rule_template，用户编辑后 source=user_edited；禁止显示真实 AI 结果。不能读取其他项目业务资料，不能从文件指令继承执行权限。确定性图检查不交给模型决定。

## 九、验收界面与纵向切片

沿用已有视觉方向，仅增加项目内“技术方案与阶段计划”页。展示基线选择、环境方法与结果、可编辑声明、方案确认、可编辑版本/阶段/任务、引用需求及验收、检查结果、历史快照。显示未保存、保存中、失败与冲突；失败保留输入，重新读取用于核对，未保存时禁用确认。

采用短延迟自动保存和显式保存；未完整输入可保留在页面，离开提示尚未保存。旧数据/来源失效时禁用依赖有效来源的确认。有阻塞图允许改草稿，不能确认；已经确认仍不能点执行，因为本轮执行能力未交付。四种宽度与键盘关键表单检查；原生缩放/真机未做仍待验。

## 十、测试要求

保留前 64 项测试；新增真实业务规则测试：基线缺失/跨项目、严格字段、方案/计划保存冲突、幂等与同键不同内容、人工确认不可变、旧环境过期、声明变化/符号链接/超长/权限限制、缺工具和命令超时、不执行仓库脚本、没有秘密全文、旧基线/新方案使确认失效、三层依赖图/父阶段循环/未知引用、覆盖遗漏及验收不能削弱、重启历史恢复、迁移旧资产保留和未提供执行接口。

实际本机链路：在明确标名的 A3 合成演示中冻结需求基线 → 环境检查 → 保存/确认方案 → 生成并编辑计划 → 引入循环显示阻塞 → 修复并确认 → 重启核对历史与来源。合成需求来源与真实本机操作分别标注；本轮无真实模型样例、不改变 A2 待验。

## 十一、产品负责人验收清单

1. 在工作台进入项目需求页，点“技术方案与阶段计划”；没有基线时应提示先确认需求。
2. 点“检查本机与项目环境”，看到方法、检测时间、版本/权限/资源、模型未启用及执行器未交付；不出现安装完成。
3. 选择冻结基线并生成规则草稿，核对并编辑技术方案，看到保存修订，明确确认后出现绑定基线的记录。
4. 生成阶段计划，查看版本、阶段与任务、需求关联、原验收要求和每阶段闸门。修改任务或依赖后看到保存状态与检查结果。
5. 依赖成环、未知引用、需求遗漏或来源失效时看到原因，确认不可操作；修复后核对并明确确认。
6. 查看历史资产；新草稿不修改旧确认，刷新及重启记录仍在。显示“可交接”不等于执行或验收完成。
